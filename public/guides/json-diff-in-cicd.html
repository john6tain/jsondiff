JSON diff in CI/CD: catching unintended config drift

Updated August 3, 2026 ~4 min read

Config files drift silently. Someone bumps a timeout on staging, a merge brings in the wrong value, an auto-formatter rewrites an env file. A diff step in your pipeline turns every accidental change into a reviewable, machine-checkable diff before it reaches production.

What config drift looks like

Config drift is the slow divergence of the same file across environments or over time. It's invisible for two reasons: nobody re-reads a config file top to bottom on every deploy, and a single changed value often doesn't break anything by itself. It just shifts behavior — a longer timeout here, a lower retry count there — until someone notices a stack has been configured differently from the rest of the fleet for three months.

The same comparison logic you use to debug an API applies here: put the known-good config on one side and the candidate on the other, and let the diff list every added, removed, and edited key with its full path.

Where to add a diff check

Three placements cover most drift:

  • Pre-deploy: compare the config about to ship against the config currently in production. The diff is your change list — reject the deploy if it contains keys nobody intended to touch.
  • Cross-environment: a scheduled job compares staging vs production. Staging and prod should match except for a short, known allowlist of keys (credentials, feature flags, URLs).
  • Generated-config: if you render config from templates, compare the rendered output against the committed baseline so a template change can't silently alter every environment at once.

A minimal pipeline step

Conceptually the check is a few lines: fetch the baseline, load the candidate, diff, and fail on unexpected differences.

Pipeline stepbash
# Fetch the last-known-good config from the running stack
baseline=$(curl -s "$PROD_URL/config.json")

# Diff it against the config about to be deployed
diffs=$(curl -s -X POST https://johnsondiff.vercel.app/api/diff \
  -H "Content-Type: application/json" \
  -d "{\"json1\": $(jq -R -s . <<<"$baseline"), \
        \"json2\": $(jq -R -s . <<<"$(cat deploy/config.json)")}")

if [ "$(jq '.diffs | length' <<<"$diffs")" -gt 0 ]; then
  echo "Config drift detected:"
  jq '.diffs[]' <<<"$diffs"
  exit 1
fi

This site exposes the same structural diff as a small POST /api/diff endpoint, returning one object per change with the path and old/new values — convenient for a script that wants structured output rather than highlights. The response shape is the classic add/edit/remove format: a removed key is { "kind": "D", "path": ["maxRetries"] }, an edit is { "kind": "E", "path": ["timeout"], "lhs": 30, "rhs": 45 }.

Allowlist the differences you expect

Not every difference is a failure. Deploy metadata like buildTimestamp or version changes on every release and shouldn't fail the check. Filter the diff by path before deciding: fail only when a change appears outside the allowlist. That's the difference between a signal and an alarm that gets muted because it fires too often.

Interpreting a failed diff

When the check fails, you now have evidence, not a hunch. Read the diff the same way you'd read a code review: is the removed key still referenced somewhere? Is the edited value inside the range the application expects? If the change was intentional, update the baseline and allowlist; if not, the diff just prevented a silent behavior change from shipping.
