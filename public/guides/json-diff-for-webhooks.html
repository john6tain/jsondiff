JSON diff for webhooks: debugging payload changes between events

Updated August 13, 2026~7 min read

Webhook bugs are hard because the failing payload usually arrives after the code that handles it has already shipped. A JSON diff between a known-good event and a failing event can show the contract change quickly.

Save real examples before you need them

The best before-value is a sanitized payload from a successful webhook. Keep fixtures for important event types: payment succeeded, subscription canceled, user updated, invoice failed. Remove secrets and personal data, but preserve shape, field names, and representative types.

What usually breaks webhook consumers

  • Missing IDs: a field used for idempotency or lookup disappears.
  • Renamed event types: routing code listens for the old string and ignores the new one.
  • Type changes: an amount changes from cents as a number to a formatted string.
  • Nested moves: customer data moves under data.object.customer or a similar envelope.
  • Array ordering: line items or status history arrive in a different order than the handler assumed.

Example: event type and amount changed

The handler may fail twice: first because the event router no longer matches invoice.paid, and again because math on amount now receives a string. The diff makes both problems visible without stepping through the whole webhook pipeline.

Sanitize without destroying the shape

Never paste secrets, tokens, or personal information into bug reports. Replace values with placeholders of the same type: keep strings as strings, numbers as numbers, booleans as booleans, and arrays as arrays. Changing 4900 to "amount" can hide exactly the type problem you are trying to diagnose.

Compare event types separately

Do not compare a subscription event to an invoice event and expect a clean result. Different event types have different shapes. Compare old and new examples of the same event type first; then compare related event types only when you are intentionally studying the differences between them.

After the diff

Turn the confirmed changes into tests. If a field became optional, add a fixture without it. If an amount type changed, add validation before math. If an event type was renamed, make routing explicit and keep a compatibility branch only as long as the sender can emit both versions.
