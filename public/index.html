What is a JSON diff?

A JSON diff is a side-by-side comparison of two JSON documents that reports exactly what changed: which keys were added, removed, or edited. Instead of eyeballing two walls of braces, you get a focused list of differences — and, in this tool, character-level highlights on the precise part of each changed line.

That matters because JSON is the lingua franca of web APIs, configuration files, and data exports. When an integration breaks or a deployment behaves differently than it did yesterday, diffing the old document against the new one is the fastest way to understand why — the cause is usually one small field, and a good diff makes it jump out in seconds. New to this? The guides walk through real scenarios step by step.

This site is maintained as an open-source resource around that workflow, not just a blank utility page. The written guides explain how to interpret the output in API debugging, CI/CD review, webhook troubleshooting, OpenAPI contract checks, lockfile review, and nested-object comparisons.

Worked examples

Four worked examples

Each example pairs a before and after payload, with changed values highlighted the way the tool flags them.

1A field type changed in an API response

An e-commerce API you integrate with switched price from a string to a number. Same digits, different type — and it breaks any code that concatenates or compares the value.

The diff flags one edited line: price went from "349.00" to 349.00. A string and a number look alike but behave differently — "349.00" + 0 yields the string "349.000", while 349 + 0 is the number 349. Type changes are a classic silent breakage in API integrations, and exactly what a structural diff catches.

2A config file added a key and changed a value

A service config gained a new maxRetries key and a longer timeout between deploys. Nothing was deleted — just one addition and one edit.

maxRetries is added and timeout edited from 30 to 45, while name and the whole cache block are identical and stay quiet. Unchanged subtrees produce no noise — that's what lets the two real changes stand out at a glance.

3A merge conflict buried in a nested object

Two teammates edited deploy settings in separate branches. The merge conflict sits inside a nested object — the diff drills down to show which keys disagree.

The diff reports deploy.instances (2 → 4) and deploy.strategy ("rolling" → "blue-green") while region stays untouched. With full paths shown, resolving the conflict is a choice between two values — not a hunt through layers of braces.

4An array was reordered

A load balancer reordered its host list. The set of hosts is identical — only the order changed.

Arrays are ordered, so a swap shows up as a removal and an addition at the changed indices. If order carries meaning (priority, queue position, sort order), that's a real change; if it doesn't, sort both arrays first and the diff goes quiet. See the guide on JSON arrays and ordering.

Edge cases

Edge cases this tool handles

Here's how this tool handles the cases that trip up naive comparisons.

Array reordering

Arrays are compared by index, so reordering elements is reported as removes and adds even when the set is unchanged. If order carries meaning — priority, queue position, sort order — that's a real change.

Nested object changes

Changes two or more levels deep are detected and shown with their full path (e.g. deploy.instances), so a buried modification is never missed.

Key order differences

JSON objects are unordered by definition. The tool parses and pretty-prints both sides before diffing, so identical objects with keys in a different order compare as identical — key order is never a difference.

null vs undefined vs missing

{"a": null} and {"a": 1} are an edit; {"a": null} and {} are a removed key. Each is reported precisely, not collapsed into a vague "something changed".

Type coercion

"1" (string), 1 (number), and true (boolean) are distinct. The tool never coerces types, so a string-to-number change is surfaced rather than silently ignored.

FAQ

Frequently asked questions

Does key order matter in JSON diff?

No. JSON objects are unordered collections of key/value pairs — {"a": 1, "b": 2} and {"b": 2, "a": 1} are the same document. This tool parses both sides and pretty-prints them before comparing, so key order is never reported as a difference. What matters is the set of keys and the values attached to them.

How do I diff JSON arrays?

Paste both documents into the two panels as usual. Arrays are compared element by element, by index: an element present on the right but not the left is reported as added, the reverse as removed, and an element that changed in place as edited. Because order is part of an array's meaning, reordering elements is reported as removals and additions at the affected indices.

Can I diff JSON against YAML?

Not directly — both panels expect JSON input. Convert a YAML file to JSON first (yq does this in one command) and paste the result. The JSON vs YAML guide covers when each format makes sense.

Is my data uploaded anywhere?

No. Both views run entirely in your browser — nothing is POSTed to any server, and the site sets no cookies and runs no tracking scripts. You can confirm it in your browser's network tab: comparing two payloads produces zero requests. See the privacy policy for the full statement.

What's the difference between the split view and the change list?

The split view aligns the two payloads side by side and highlights the exact changed characters in each changed line. The change list is a structured table: one row per added, removed, or edited field, with the full path and old and new values. Use the split view to read a diff; use the change list to copy a summary into an issue or PR.

Why does a reordered array show as removed and added?

Because arrays are ordered, and the diff reports changes by index. Swapping elements changes their indices, so the old value disappears from one index and a new one appears at another. If order doesn't matter to you, sort both arrays first and only real differences remain.

Does the tool handle large JSON files?

It's designed to stay responsive on typical payloads. For very large documents the split view switches to a linear comparison mode, so it keeps working but pairs similar lines less aggressively. For multi-megabyte files, compare the relevant subtree rather than the whole document.
